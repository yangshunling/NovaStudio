## 1. 结论先行

卡顿不在主进程的 SQL，也不在 Git 调用，而集中在**渲染进程把「全量内容」反复做成了同步工作**：

| 排名 | 问题 | 用户感受 | 本轮处理 |
|---|---|---|---|
| P0-1 | 长会话按「120 条消息」开窗，而不是按内容成本开窗 | 点开长会话卡 1–3 秒 | ✅ 已修 |
| P0-2 | 流式正文每次刷新整段重新 Markdown 解析 | 长回复越写越卡、文字成块蹦 | ✅ 已修 |
| P1-3 | 流式期间 Store 每 16ms 换 `streamingBySession` 引用 | 会话列表最高 60 次/秒重渲染 | ✅ 已修 |
| P1-4 | 工具卡片 / 思考卡片未 memo，随每个 token 全量 diff | 工具调用多的回复发烫、掉帧 | ✅ 已修 |
| P1-5 | 工作流实时运行页每个 token 一次整页 `setState` | 查看运行中节点时卡顿 | ✅ 已修 |
| P1-6 | 生产包未压缩：5.24 MB / 8.6 万行 JS | 冷启动白屏更久 | ✅ 已修（3.82 MB） |
| P1-7 | 文本 delta 按 16ms 刷新 store，但可见文本只按 80–200ms 变化 | 流式期间整条链路空转 | ✅ 已修（48ms + 结构事件直通） |
| P1-8 | `MessagePrimitive.Parts` 内联 components / 运行时 store 每帧换引用 | 击穿 assistant-ui 的 memo | ✅ 已修 |
| P1-9 | Git 提交框每敲一个字重算整份 diff 并重建所有 diff 行 | Git 页输入发涩 | ✅ 已修（DiffView memo） |
| P2-6 | 会话历史合并 O(n×m) | 长会话追加重连时慢 | ✅ 已修 |

一句话：**单帧工作量从 O(全文) 降到了 O(尾部)，打开长会话从 O(全会话) 降到了固定预算。**

## 3. 已实施优化（带证据）

### P0-1 会话打开：从「按条数开窗」改为「按渲染预算开窗」

- 位置：`src/renderer/components/chat/AssistantMessageList.tsx:79-146`、`:182-200`、`:292-296`
- 原实现：`INITIAL_MESSAGE_WINDOW = 120`，从末尾切 120 条。
- 问题：条数与成本无关。最大会话 40 条消息、143 万正文，120 条窗口等于全量挂载，Markdown 解析约 2.3 s，期间主线程完全阻塞。
- 修法：
  - 从末尾向前累加**渲染权重**（正文/思考字符数 + 每个事件 120 权重），上限 `INITIAL_TEXT_BUDGET = 120_000`；
  - 最后一条消息无论多大都保留，避免空白；
  - 「载入更早」也按预算分批（`LOAD_EARLIER_BUDGET = 80_000`，单次最多 40 条）；
  - 窗口起点只随会话/消息数变化重算，不跟随每个 token。
- 预期收益：最大会话打开成本从约 2.3 s 降到约 0.2 s（约 10 倍），且与历史长度解耦。

### P0-2 流式正文：从「每帧整段解析」改为「稳定块 + 增长尾巴」

- 位置：`src/renderer/lib/markdown-blocks.ts`（新增）、`src/renderer/components/ui/MarkdownRenderer.tsx:335-376`
- 原实现：`useThrottledValue` 每 80–200 ms 把**全量正文**交给 `react-markdown`。
- 问题：32 KB 时单帧 50 ms，92 KB 时 153 ms。200 ms 刷新一次意味着主线程 25%–75% 的时间在做重复解析，长回复必然掉帧。
- 修法：
  - 超过 8,000 字符的正文按安全边界切块：已完成块交给 **memo 化的 `MarkdownRenderer`**，每帧只重解析最后一块；
  - 安全边界规则：不切围栏代码块内部、不切松列表条目之间、不切列表缩进续行；出现引用式链接定义（`[id]: url`）时整体放弃切分；
  - 块级渲染共用一个 `.nova-markdown` 容器（`bare` 模式），保证 `mb-*` 与首尾边距规则与整段渲染一致；
  - 结束时不切回整段渲染，避免整棵树卸载重建。
- 实测：92 KB 正文单帧从 153 ms 降至约 1 ms（切分 0.6–1.1 ms + 尾块渲染 0.2 ms）；新增 9 条切分规则单测。
- 风险控制：切分器只做保守切分；引用定义 / 代码围栏 / 列表三类高风险结构均有测试覆盖。

### P1-3 Store 每 16ms 无条件换切片引用

- 位置：`src/renderer/stores/chat.ts:250-315`
- 原实现：`flushPendingEvents` 每次都 `{ ...state.streamingBySession }`、`{ ...state.usageBySession }`。
- 问题：会话列表订阅整个 `streamingBySession`（`SessionListPanel.tsx:158`），Zustand 以 `Object.is` 判断选择器结果 → 每 16 ms 重渲染整个会话列表，即使流式状态没变。
- 修法：只有真正写入新状态时才克隆对应切片，未变化的切片保持原引用。
- 收益：流式期间会话列表因 token 触发的重渲染从最高约 60 次/秒降到 0（仅会话本身变化时才渲染）。

### P1-4 工具卡片随 token 全量重渲染

- 位置：`ToolCallCard.tsx:55-90`、`ThinkingCard.tsx:17`、`AssistantMessageList.tsx:547-563`、`:755-768`
- 问题与修法：
  1. `ToolCallCard` / `ThinkingCard` 未 memo → 已用 `memo` 包裹；
  2. `readResultImages` 每次渲染返回新数组，导致 memo 失效 → 改为按 `result.images` 引用缓存；
  3. 工具参数的 `JSON.stringify` 每次转换都重跑 → 用 `WeakMap` 按 `event.input` 对象缓存（大文件编辑参数可达数十 KB）；
  4. 增删行统计原来两次 `reduce + filter` → 改为一次遍历 + `useMemo`。
- 收益：一次回复里几十张已完成工具卡片不再跟着每个 token 做 DOM diff。

### P1-5 工作流实时运行页的每-token 整页更新

- 位置：`src/renderer/components/workflows/WorkflowRunView.tsx:337-384`
- 原实现：每个 `workflow:run:agentEvent` 直接 `setLiveMap`。
- 问题：主进程批量队列只是「攒一批再发」，批内仍是逐条 IPC；渲染进程每个回调都是独立任务，React 无法跨任务合批 → 每秒几十次整页重渲染。
- 修法：与聊天流一致，在渲染侧以 16 ms 窗口合并事件，一次 `setLiveMap` 应用整批。
- 收益：该页面刷新频率从「每 token」降到「每帧」。

### P2-6 会话历史合并 O(n×m)

- 位置：`src/renderer/stores/chat.ts:492-500`
- 原实现：`existing.filter(m => !history.some(item => item.id === m.id))`。
- 修法：先建 `historyIds` Set，再过滤。长会话重连时由 O(历史 × 新消息) 降为 O(历史 + 新消息)。

### P1-6 生产包未压缩（冷启动最大的单项）

- 位置：`electron.vite.config.ts:41-53`
- 原实现：electron-vite 的 renderer 预设默认 `minify: false`，项目未覆盖。
- 证据：构建产物 `index-*.js` 5,241,744 B / 86,453 行，函数名与注释完整保留；CSS 150.9 KB。`<script type="module">` 是 deferred，HTML/CSS 先画出空白 root，随后主线程要解析执行完整 JS，React 才能挂载。
- 修法：`build.minify: "esbuild"`（CSS 随之压缩）。
- 实测：JS **5.24 MB → 3.82 MB**（-27%），CSS **150.9 → 110.5 KB**（-27%）；无行为变化。
- 备注：仍建议后续配合 `manualChunks` + 非首屏页面 `React.lazy`，见 P2-1。

### P1-7 文本刷新频率与可见刷新频率不匹配

- 位置：`src/renderer/stores/chat.ts:225-250`、`:757-782`
- 原实现：所有事件统一 16ms flush；而 `AnswerPart` 的可见文本按 80–200ms 节流。中间每一帧都会触发 assistant-ui 的 `setAdapter → _updateStoreSnapshot` 与整窗转换缓存检查，60Hz 的固定开销买不到可见收益。
- 修法：文本 / 思考 / usage 合并到 **48ms（约 20Hz）**；工具调用、工具结果、错误、`message_end` 等结构性事件**立即 flush**，不延迟工具卡片。
- 收益：纯文本流式期间的全链路渲染从最高 60Hz 降到约 20Hz，可见打字节奏不变。

### P1-8 assistant-ui 的组件表与运行时 store 引用不稳定

- 位置：`AssistantMessageList.tsx:84-100`、`:335-353`
- 问题：`MessagePrimitive.Parts` 的 `components` 是内联字面量；`useExternalStoreRuntime` 的 store 也是每次渲染新建的对象。前者破坏官方逐项 memo，后者让 `setAdapter` 无法命中 `_store === store` 的早退。
- 修法：components 表提到模块作用域；store 对象用 `useMemo`，`onNew` 用模块级空实现。
- 收益：无关重渲染不再触发整窗快照更新和 parts 分发。

### P1-9 Git 提交框击键触发整份 diff 重算

- 位置：`src/renderer/components/workspaces/GitTab.tsx:141-152`、`:1155-1162`、`:1866-1878`
- 问题：`message` 是 GitTab 根状态，每敲一个字整页重渲染；`DiffView` 未 memo，每次重新 `split("\n")`、两次 `filter`、逐行正则与行号计算；`diff.trim()` 也每次整串扫描。
- 修法：`DiffView` 加 `memo`；`hasDiff` 用 `useMemo` 按 diff 缓存。
- 收益：提交信息输入不再触发 diff 解析与数千行 VDOM diff。
- 说明：变更文件列表（`ChangeGroup`）仍会随根状态重渲染，彻底隔离提交框状态列入批次 3。

### 补充：流式结束时的 Shiki 高亮尖峰已被块级渲染摊平

原实现中所有代码块在 `streaming=false` 的那一帧集中同步高亮。块级渲染后，已完成块在写完时各自高亮一次，结束时只剩尾块需要处理。短消息（< 8 KB）仍是整段渲染，但代码块数量有限，影响可忽略。

## 6. 已确认「不需要改」的部分

避免下一轮重复投入：

- **SQLite**：`messages(session_id, timestamp)`、`sessions(updated_at)` 部分索引、workflow 三类查询索引、`knowledge_documents(kb_id)` 均在；使用 WAL + 外键；已实现 prepared statement 缓存（`sqlite.ts:71-81`）。
- **Git**：全部 `execFile` 异步调用，无 `spawnSync`；状态读取按需触发。
- **文件系统**：主进程无同步递归扫描热路径；文件树按目录懒加载；知识库/技能扫描均为 `fs/promises`。
- **Shiki**：按需语言清单 + LRU 缓存（160 条 / 2 MB）；流式期间跳过高亮。
- **长列表**：会话列表、待办、知识库、Git 文件、运行记录均已使用 `content-visibility: auto`。
- **知识库检索**：FTS5 trigram + 250 ms 防抖，不是逐键 IPC。
- **聊天流**：主进程 16 ms 聚合 + 渲染侧文本 48 ms / 结构事件直通；会话切换不重复回读全量历史；`convertMessage` 引用稳定。
- **构建**：renderer 已开启 esbuild 压缩；仍未分包（见 P2-1）。
- **无问题的轮询**：触发器/工作流调度为逐次 `setTimeout` 重武装，不在 UI 线程做重活。

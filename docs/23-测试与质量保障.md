# 23 测试与质量保障

## 1. 测试体系

项目使用 Node 原生测试运行器（`node --test`），不引入 Jest / Vitest。

```json
"test": "node --test tests/agent-events.test.ts tests/parse.test.ts tests/history.test.ts tests/image-input.test.ts tests/permission-prompt.test.ts tests/protocol.test.ts tests/trigger-schedule.test.ts tests/graph.test.ts tests/mcp.test.ts tests/execution-report.test.ts tests/batch.test.ts tests/upgrade.test.ts tests/markdown-blocks.test.ts tests/report.test.ts"
```

### 1.1 为什么不用 Jest

- 测试对象主要是纯函数与独立模块；
- Node 20 原生 `node --test` 足够；
- 减少依赖与配置；
- 部分测试用 `esbuild` 现场打包 TS 模块，避免引入完整构建链。

### 1.2 运行

```bash
npm test
npm run typecheck
npm run build && npm run verify:skins
```

## 2. 测试文件清单

### 2.1 `tests/agent-events.test.ts`

对象：`shared/agent-events.ts` 的 `appendEvent`。

覆盖：

- `text_delta` 追加到末尾同类型块；
- `thinking` 与 `text` 增量不会互相覆盖；
- `message_end` 替换末尾累积块，保留工具结果；
- 完整 `text` 块始终新建段落。

**为什么重要**：事件收敛是流式渲染与历史回放一致性的基础。收敛规则错了会出现重复正文、丢失思考、工具块被吞。

### 2.2 `tests/parse.test.ts`

对象：`claude/parse.ts` 的解码器 + `appendEvent`。

测试方式：用 `esbuild` 把 TS 模块打成临时文件再导入。

覆盖：

- 工具回执穿插在同一条 assistant 消息中时，不会重复累积块；
- Bash 等命令类工具同样进入消息流，正文既不重复也不丢失；
- 同一段内的增量仍由 `message_end` 收敛，不产生重复。

**为什么重要**：Claude 的 assistant 事件按 content block 逐条发送，并行工具调用时回执可能夹在中间。这是最容易写出重复内容的地方。

### 2.3 `tests/protocol.test.ts`

对象：`agents/line-run.ts` + `transport.ts` + `resume-error.ts` + `parse.ts`。

覆盖：

- 非零退出：stderr 作为诊断上报，写入 `RunResult.error`；
- 非零退出但没有 stderr：给出退出码错误，不再静默；
- stdout 与 stderr 交错不会拼坏 stdout 的 JSON 行；
- Windows 下参数中的 `&` 不会被 cmd 拆成额外命令；
- 进程已 exit 但孙进程持有管道时，500ms 兜底收尾；
- `result` 错误子类型上报为 error；
- 识别 resume 失效文案；
- `result` 成功子类型不产生事件。

**为什么重要**：进程传输层的边界条件最多，且直接决定“运行会不会卡住 / 失败被误判”。

### 2.4 `tests/trigger-schedule.test.ts`

对象：`shared/trigger-schedule.ts`。

覆盖：

- 损坏规则回退每天 09:00；
- interval 分钟数夹到 1–1440；
- weekly 无有效星期回退工作日；
- daily 严格返回晚于 `from` 的时刻；
- weekly 只在选中的星期触发；
- interval 从 `from` 起算；
- 规则摘要可读。

### 2.5 `tests/graph.test.ts`

对象：`shared/workflow-graph.ts`。

覆盖：

- 合法串行图返回拓扑序与直接前驱；
- 拒绝环；
- 拒绝未绑定 / 停用的员工与不可达节点；
- 必须只有一个开始节点和一个结束节点；
- 结束节点必须有入边、开始节点不能有入边；
- 执行节点必须能到达结束节点，悬空的结束节点也会被拒绝；
- 分支不会阻断运行，但会提示并行写文件的冲突风险。

### 2.6 `tests/mcp.test.ts`

对象：`shared/mcp.ts`。

覆盖：

- `splitArgs` 支持单双引号；
- `parseKeyValueLines` 忽略空行、注释与无等号行；
- `formatKeyValue` 与 `parseKeyValueLines` 往返一致。

### 2.7 `tests/execution-report.test.ts`

对象：`workflow/execution-report.ts`。

覆盖：

- 执行报告包含配置、注入清单、命令行与结果；
- 敏感环境变量值不会写入报告；
- 未获取到调用信息时明确说明。

### 2.8 `tests/batch.test.ts`

对象：`ipc/batch.ts`。

覆盖：

- 窗口内多条事件合并成一批，顺序保持入队顺序；
- `flush` 立即发送并取消定时器，同一批不会重复发送；
- 空队列 `flush` 不触发发送；
- `flush` 期间重入入队的内容留到下一批。

**为什么单独抽模块**：`push.ts` 依赖 Electron 窗口，无法在 `node --test` 里直接验证；`batch.ts` 不依赖 Electron，可独立测试。

### 2.9 `tests/history.test.ts`

对象：`claude/sessions.ts` 的 `readHistory`（用临时 `configDir` 造真实 JSONL）。

覆盖：

- 文本 / thinking / tool_use / tool_result 正确还原；
- `usage`、`message_end` 等记录不重复产生正文；
- 损坏行跳过，不影响其它消息；
- 会话文件路径按 cwd 转义规则定位。

### 2.10 `tests/image-input.test.ts`

对象：`claude/input.ts`。

覆盖：

- 无图片时保持纯文本 stdin；
- 有图片时生成单行 NDJSON 用户消息，图片在前、正文在后；
- 多张图片保持顺序；
- 空正文 + 图片仍可发送。

### 2.11 `tests/permission-prompt.test.ts`

对象：`claude/parse.ts` / `input.ts` / `permission.ts` / `shared/permission.ts`。

覆盖：

- `can_use_tool` 控制帧解析；
- `control_response` 编码形状；
- 允许时回传 `updatedInput`，拒绝时带提示；
- 权限模式是否可能询问（`modeMayAsk`）；
- 超时 / 中断的失效应答。

### 2.12 `tests/upgrade.test.ts`

对象：`claude/upgrade.ts`。

覆盖：

- 版本号按数字段比较，不按字符串；
- 忽略 `v` 前缀与尾随说明；
- 同版本时稳定版高于预发布版。

### 2.13 `tests/markdown-blocks.test.ts`

对象：`renderer/lib/markdown-blocks.ts`。

覆盖：

- 按空行切分稳定块与尾部；
- 围栏代码块内部的空行不是块边界；
- 松列表、引用块等结构不被拆散；
- 流式增长时只重解析尾部。

### 2.14 `tests/report.test.ts`

对象：`shared/report.ts`。

覆盖：

- 本周从周一 0 点开始，共 7 天；
- 上周 / 最近 7 天 / 自定义区间边界；
- 周报 prompt 包含待办、备注、完成状态；
- Markdown 导出清洗；
- 周期内无记录时的空结果。

## 3. 类型检查

```bash
npm run typecheck   # tsc --noEmit -p tsconfig.json
```

严格选项：

- `strict`
- `noUnusedLocals`
- `noUnusedParameters`
- `noFallthroughCasesInSwitch`
- `noImplicitReturns`

**约定**：提交前必须通过。类型检查是最便宜的回归防线。

## 4. 皮肤校验

### 4.1 运行时（开发模式）

`App` 启动时 `validateSkins()`：

- 探针元素逐套皮肤读取 `getComputedStyle`；
- 检查 `REQUIRED_TOKENS` 是否都能解析；
- 缺失在控制台报警。

### 4.2 构建后

```bash
npm run build
npm run verify:skins
```

`scripts/verify-skin-tokens.mjs` 检查：

1. 每套皮肤能解析全部必填 token；
2. `_base.css` 使用 `:where([data-theme])`；
3. CSS 里出现的每个 `--c-*` 都登记在契约里。

详见 19。

## 6. 建议的 CI 流程

当前仓库没有 CI 配置。复刻时可加：

```yaml
steps:
  - npm ci
  - npm run typecheck
  - npm test
  - npm run build
  - npm run verify:skins
```

打包与发布可单独 workflow，需要 GitHub Token 与 Windows runner。

## 7. 覆盖缺口

以下模块没有单元测试，主要依赖手工验证：

- `db/repositories/*`（大量 SQL）；
- `workflow/runner.ts`（DAG 调度 / 审核 / 续跑）；
- `agents/agent-service.ts`（运行编排 / 历史缓存）；
- `automation/scheduler.ts`（轮询 / 并发 / 停止）；
- `files/watcher.ts`（目录监听与合并）；
- `knowledge/catalog.ts`（扫描 / 索引 / 检索）；
- `skills/catalog.ts`（frontmatter / 导入）；
- `mcp/catalog.ts`（读写 / 改名）；
- 所有渲染层组件。

复刻时建议优先补：

1. 图调度 / 审核状态机的集成测试；
2. schema 版本号与旧库重建的测试；
3. 知识库 FTS / 降级的测试；
4. 员工运行时同步与旧版临时目录清理的测试。
